# Дорожная карта «Сладкой»

Обновлено: 2 августа 2026 года.

Главный порядок работ: **датчик → вычислительное ядро → сохранение состояния →
проверенное показание → тревоги → передача семье → интерфейс**. Видимые экраны не
считаются прогрессом к реальному датчику, пока этот тракт не доказан.

Каждый шаг выполняется по TDD: сначала фиксируется ожидаемое поведение эталона и
пишется автоматическая проверка, затем добавляется минимальный код, после
совпадения проводится рефакторинг.

Текущий приоритет владельца: собрать один полный вертикальный цикл до первого
реального устройства. Поэтому после зелёного контрольного среза работы идут не
по косметике и не по новым редким случаям ядра, а по цепочке
`активная конфигурация → product BLE → Room → число/график → тревога/виджет →
backend → сайт/Telegram`.

## Этап 0 — зафиксировать эталон

Статус: **выполняется; программная часть эталона закреплена**.

Делаем:

- закрепляем конкретный commit исследовательского upstream и хеши нативных
  библиотек производителя;
- воспроизводимо собираем контрольный APK без изменения сенсорного поведения;
- описываем матрицу GS1, GS1Sb и GS3: код упаковки, subtype, версия протокола,
  версия алгоритма и формат состояния;
- создаём формат private sensitive evidence: входные BLE-пакеты, порядок, время,
  результат, тренд, предупреждения и бинарное состояние; реальный capture не
  хранится в Git;
- текущий неподтверждённый драйвер продукта оставляем в диагностическом
  карантине; интерфейс развивается только на изолированном демо и не открывает
  продуктовый сенсорный поток.

Уже выполнено:

- закреплён commit исследовательского эталона;
- получены официальные международный и китайский APK, проверены package,
  версия, сертификат и SHA-256;
- выполнен глубокий read-only аудит текущего международного APK: закреплены
  onboarding через DataMatrix/8-символьный код, JNI ABI, native state, BLE UUID,
  точный V120 envelope и честные границы защищённого Java-слоя;
- наборы алгоритма `v116A`/`v115G` и транспортный обработчик для `arm64-v8a` и
  `armeabi-v7a` включены в отдельные модули с обязательной проверкой хешей;
- зафиксированы точные Java/JNI-классы и сигнатуры;
- сырой GS1 sample отделён от готового показания и не может попасть на экран.

Результат: одна закреплённая контрольная версия, с которой можно доказуемо
сравнивать каждое следующее изменение.

## Этап 1 — узкий адаптер нативного ядра GS1/GS1Sb

Статус: **выполняется**.

Сначала проверки:

- загрузка только ожидаемой версии и ABI библиотеки;
- `init → process → get state → restart → set state → process`;
- строгая последовательность измерений;
- пропуск, дубль, повреждённый пакет и повреждённое состояние;
- проверка 8-символьного кода сенсора, обычного декодирования чувствительности и
  точного fallback ко второму декодеру только при результате `-1.0`;
- атомарная фиксация результата и нового состояния.

Затем код:

- минимальные Android/JNI-классы с точными полями, которые ожидает официальная
  библиотека;
- отдельные драйверы GS1 и GS1Sb за общим интерфейсом;
- сохранение исходного результата, тренда, предупреждений, версии ядра и
  происхождения измерения;
- запрет на догадки: неизвестная версия или неоднозначный пакет дают «данных
  нет», а не запасное значение сахара.

Результат: тестовый модуль получает на одинаковом входе тот же результат и то же
состояние, что закреплённый эталон. Он ещё не управляет тревогами мамы.

Уже выполнено:

- тесты ABI, профиля, размера и хеша состояния, строгой последовательности,
  ошибок JNI, восстановления и жизненного цикла контекста;
- двухфазный барьер сохранения: следующая точка запрещена до подтверждения
  записи checkpoint;
- код сенсора ограничен восемью ASCII-буквами или цифрами, сохраняет регистр и
  никогда не заменяется другим идентификатором;
- подтверждён и реализован обычный путь инициализации в режиме `0`, а также
  отдельный native entry point альтернативного режима для обоих закреплённых
  алгоритмических профилей;
- второй декодер вызывается только после точного `-1.0` от обычного. Его
  encoding и режим не смешиваются с обычным: вся калибровочная tuple сохраняется
  в binding/result/checkpoint и проверяется при reopen; физическая parity
  альтернативного режима ещё не доказана, поэтому результат остаётся только
  диагностическим;
- официальный транспортный обработчик получил безопасный фасад для регистрации,
  авторизации, активации, времени, запроса данных, reset и split;
- GS1/GS1Sb-команды строятся официальным обработчиком, а вход алгоритма
  принимается только при совпадении официального и независимого парсеров;
- создан координатор `sample → алгоритм → атомарное хранилище → подтверждение`;
- атомарное Room-хранилище поддерживает идемпотентный точный повтор, отвергает
  конфликтующие дубли и не допускает откат checkpoint;
- первая и единственная Room-схема `v1` сразу хранит происхождение транспортного
  тракта и canonical MAC физического сенсора;
- append-only ingress сохраняет каждый принятый шифрованный notification до
  декодирования; runtime принимает только пакет с durable receipt;
- raw sample имеет обязательный FK `sourceIngressId`; core commit сверяет exact
  sensor/family/MAC/time/bytes/hash до любых записей;
- отдельная таблица outcomes делает статус каждого ingress идемпотентным;
  pending-пакеты восстанавливаются до нового GATT-подключения по фактическому
  cursor ядра, включая переставленные пакеты, разрывы и остановку на неизвестной
  протокольной команде;
- covered/partial recovery читает полный ожидаемый prefix только из Room и
  повторно выдаёт product lineage до outcome; packet не вычисляет publication;
- отдельный журнал сохраняет отказ до нативного вызова и неоднозначный исход
  записи, а точный повтор не вызывает алгоритм второй раз;
- многоточечный пакет проверяется целиком до первого шага ядра и обрабатывается
  последовательно от сохранённого индекса;
- диагностический результат отделён от продуктового показания типом и никогда
  не создаёт запись для экрана, тревоги, виджета или отправки;
- исправлен точный V120 envelope `L=11+8*N`; trailing bytes и обрывы запрещены;
- добавлен отдельный строгий V115 envelope, одноразовый стартовый запрос истории,
  sensor-driven дальнейшие notifications и точное время по
  receive-time/add-time/reindex с индивидуальным future-clamp;
- создан диагностический core runtime с bounded FIFO, exact retry, drain/join и
  generation-защитой GATT identity;
- state machine проверяет порядок ACK и не двигает cursor до durable commit;
- Android GATT-supervisor проверяет endpoints и generation, сериализует command
  writes, ограничивает каждую фазу deadline, ограничивает auth retry, закрывает
  Bluetooth до ожидания базы и автоматически переподключается с bounded
  exponential backoff;
- generation, identity, bind и close сведены в один атомарный GATT-registry;
  fake-GATT тесты покрывают callback до возврата `connectGatt`, stale callback,
  параллельный stop и exactly-once release, а endpoint проверяется только после
  identity gate; глобальный identity-owner и weak tombstone запрещают передачу
  одного объекта между lease и повторную привязку во время release;
- терминальный core-result больше не запускает уже принятый хвост через тот же
  native context; первая причина сбоя сохраняет приоритет при callback/actor
  гонке; история и прогрев не объявляются свежим диагностическим потоком;
- `V116A` хранит точный start сенсора как immutable checkpoint provenance и
  проверяет `sensorTime = start + index × 60 секунд` до JNI; публикация возможна
  строго после 45 минут. `V115G` не получает выдуманный общий прогрев;
- внутренний approved coordinator сохраняет warmup/history как state-only и
  создаёт measurement/outbox только для свежего `VALID`; терминальная ошибка
  после checkpoint-commit сразу закрывает runtime без потери подтверждённого
  префикса;
- обычный запуск Android работает fail-closed, демо запускается отдельно и не
  сохраняется в Room/виджет, не загружается на backend и не создаёт удалённые
  тревоги; backend также отклоняет `simulator` на продуктовом endpoint;
- добавлена строгая сохраняемая state machine onboarding GS1/GS1Sb: ручной ввод
  и декодированный DataMatrix принимают один и тот же точный 8-символьный ASCII-
  код, BLE-кандидаты проходят существующую регистрозависимую политику, а
  no-match, повреждённый MAC и неоднозначность не выбирают устройство;
- уникальный программный кандидат создаёт только профиль
  `PENDING_DIAGNOSTIC`; restart повторно проверяет snapshot и не может превратить
  его в подтверждённую конфигурацию или включить продуктовую публикацию; draft
  использует отдельное от confirmed-настройки SharedPreferences-хранилище и
  checksummed versioned codec с fail-closed разбором;
- непроверенный экспериментальный scan-first/GS3 обходной драйвер удалён из
  продуктового модуля;
- ARM64 ELF выровнены под 16-КБ страницы с доказанным сохранением payload и
  закреплёнными исходными/итоговыми SHA-256;
- APK собирается с закреплёнными нативными библиотеками;
- создан versioned golden trace `v1` для synthetic fixture и закрытых private
  GS1/GS1Sb ingress,
  ожидаемых raw samples, диагностического native output/trend/warnings и хеша
  состояния; parser fail-closed отвергает неизвестную версию, повреждение,
  обрыв, хвост и конфликт порядка;
- planner/runner сравнивает decoder и stateful algorithm через существующие
  интерфейсы, включая context close/reopen между attempt, и fail-closed проверяет
  точную пару encoding/init mode, sensitivity metadata и HMAC точного
  8-символьного входа. Пока
  fixture только явно синтетический и не является эталоном показаний.

Осталось до результата этапа:

- физический trace onboarding `код → BLE identity → точный MAC`; программный
  контур до `PENDING_DIAGNOSTIC` готов, но текущая name-suffix политика остаётся
  только кандидатом до проверки отдельного датчика;
- реальный порядок GATT callback/lifecycle на Samsung; JVM fake-transport
  контур уже реализован и не заменяет физический Android-прогон;
- instrumentation-тесты текущей Room `v1`, включая
  checkpoint + pending ingress, `close → reopen → next commit → second reopen`,
  реализованы и компилируются; локальный Emulator `37.1.11` установлен, но ARM
  system image требует отдельного принятия владельцем лицензии Google, после
  чего остаётся runtime-прогон на Android;
- recovery fail-closed проверяет sensor ID, family, Bluetooth address, exact
  raw prefix и publication lineage; несовпадение не вызывает алгоритм и не
  закрывает ingress;
- безопасная дедупликация нового ingress должна доказать earlier exact ingress
  с durable outcome; до отдельного BLE duplicate/reconnect test она блокируется
  fail-closed;
- физическое восстановление после смерти процесса и продолжение полного sensor
  replay на Android;
- ARM-инструментальный тест реальных JNI-библиотек на 4-КБ и 16-КБ устройствах;
- реальный private golden-набор вне Git, ARM-прогон закреплённых JNI-библиотек и
  побайтовое сравнение с эталоном; программный replay-контур уже готов, но
  синтетический fixture не закрывает этот барьер.

## Этап 2 — раннее физическое испытание GS1/GS1Sb

Делаем:

- подключаем отдельный датчик к контрольному Samsung;
- записываем полный жизненный цикл, включая фон, блокировку экрана,
  переподключение, пропуски, историю и перезагрузку телефона;
- сравниваем эталон и новый адаптер измерение за измерением;
- отдельно проверяем обновление приложения при активном сенсоре;
- любое расхождение превращаем в воспроизводимый тест до исправления кода.

Результат: решение по каждой проверенной модели — «совпадает», «требует
исправления» или «пока не поддерживается».

## Этап 3 — отдельный тракт GS3

GS3 не проводится через алгоритм GS1/GS1Sb. Для него отдельно фиксируются:

- код/NFC и account binding;
- Bluetooth-авторизация и последовательность команд;
- извлечение значения, время, прогрев, история и восстановление связи;
- китайский и международный варианты;
- replay-сравнение и полный цикл отдельного физического датчика.

Результат: GS3 получает собственный допуск; наличие кода в эталоне само по себе
допуском не является.

## Этап 4 — данные и локальные тревоги продукта

Статус: **approved core, атомарный measurement/outbox, общий GATT product facade,
Keystore и WorkManager готовы по отдельности; configured service и долговечные
локальные post-commit эффекты ещё не замкнуты**.

Только поверх подтверждённого результата:

- вводим модель свежего, устаревшего и отсутствующего показания;
- сохраняем сырой результат ядра отдельно от возможной ручной коррекции;
- делаем график с настоящими разрывами;
- добавляем сохраняемые настройки порогов;
- проверяем звук, вибрацию, повтор, подтверждение, перезапуск и фон на Samsung;
- подключаем большое число, график и виджет к проверенному источнику.

Уже выполнено на строго отделённом демо:

- большой показатель расположен выше графика;
- свежесть учитывает время датчика и телефона;
- график использует реальное время и не соединяет пропуски;
- пороги low/high и время потери данных сохраняются в checksummed формате;
- активная неподтверждённая тревога повторяется каждые две минуты, а
  подтверждение приглушает только текущий эпизод;
- при заблокированных Android-уведомлениях приложение показывает явное
  предупреждение и ссылку на системные настройки;
- демо-значения не сохраняются и не отправляются наружу.

Ручная калибровка остаётся отдельным выключенным модулем, пока для неё не будут
утверждены правила и собственный набор тестов.

До включения реального источника программно требуются:

- разделить проверенный reusable profile, точную activation одноразового сенсора
  и remote route; текущий exact approval не подходит для штатной замены сенсора;
- добавить долговечный local-effects cursor/outbox, подключить product GATT
  facade к configured foreground service и вызывать его explicit ack только
  после durable применения batch;
- восстановить из Room 288 точек, alarm/watchdog/widget после смерти процесса;
- реализовать Room-адаптер `BlockedUploadRecoveryPort` по exact credential tuple
  и соединить provisioning с remote route;
- добавить authenticated/signed parser provisioning-конверта; внутренний
  `RemoteProvisioningPayload` только безопасно владеет и стирает bytes, но сам
  не утверждает, что источник проверен;
- вызвать post-commit WorkManager hook из product service; готовые Keystore,
  retry/reconciliation и `APPEND_OR_REPLACE`-цепочка не должны оставаться
  изолированными компонентами.

## Этап 5 — семья, сайт и Telegram

Статус: **backend и закрытый демо-сайт реализованы на тестовых данных; связка с
реальным Android-потоком не открыта**.

Делаем:

- соединяем подтверждённый поток Android с backend;
- подключаем сайт к API и показываем большое число, свежесть и график с
  разрывами;
- восстанавливаем активные тревоги и очередь после перезапуска;
- проверяем тестовую, затем настоящую доставку Telegram;
- добавляем browser-safe BFF/session и закрытое размещение без передачи
  family token в браузер.

Результат: локальная тревога работает независимо от интернета, а семья видит
состояние удалённо. Сайт не считается единственным каналом экстренного
оповещения.

Уже выполнено программно:

- backend атомарно сохраняет измерение, изменения тревог и Telegram outbox;
- backend поддерживает несколько семей: хешированный device token разрешается
  в точный device→patient, family-session ограничивает доступ своей семьёй, а
  Telegram-получатели принадлежат конкретной семье;
- проверены точный duplicate, конфликты event ID и
  `patientId + sensorId + sequence`, конкурентные записи и восстановление
  signal-loss после перезапуска;
- только `VALID` влияет на snapshot/свежесть; `warming_up` и `degraded` не
  закрывают signal-loss;
- опубликован закрытый демо-сайт с большим значением и графиком, который не
  соединяет тестовый разрыв;
- подготовлена typed API boundary: trusted patient scope, свежесть, `VALID`,
  clock mismatch и согласованность snapshot/history проверяются fail-closed;
- при смене датчика/семейства, пропуске sequence или отброшенной точке web-график
  начинает новый сегмент; out-of-contract небезопасный sequence не может скрыть
  конкурирующее показание;
- контракт `sequence` синхронизирован: JSON integer безопасен до
  `9 007 199 254 740 991`, и та же граница действует в Go, PostgreSQL, OpenAPI и
  web;
- настоящий Telegram и браузерная семейная session пока не подключены; backend-
  авторизация семей уже реализована и протестирована локально.

Перед сетевым live-подключением остаётся выбрать server-side BFF/session, не
передающий family token JavaScript. Семейный API уже принимает token только из
`family_session`; issuer должен выставлять `HttpOnly`, `Secure` и
`SameSite=Strict`. До публичного deploy также обязательны rate limit и
пагинация либо жёсткий лимит строк history; окно до 90 дней само по себе не
ограничивает стоимость ответа.

## Когда нужен владелец

- Для этапа 0 внешние доступы не нужны.
- Перед первым физическим испытанием нужны конкретный отдельный датчик, его
  упаковка/коды и контрольный Samsung.
- Перед настоящим Telegram нужны bot token и выбранный тестовый чат.
- Git-репозиторий и его граница уже утверждены владельцем.
