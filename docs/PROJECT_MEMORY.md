# Память проекта «Сладкая»

Обновлено: 1 августа 2026 года.

## Продукт

«Сладкая» — лёгкое Android-приложение и семейный веб-интерфейс для наблюдения за глюкозой. Основной сценарий: датчик у мамы, локальная тревога на её телефоне, удалённое наблюдение семьи через сайт и тревожные сообщения в Telegram.

## Решения владельца

- Финальные продуктовые решения принимает владелец.
- Первая мобильная платформа — Android; первый телефон для физической проверки — Samsung.
- Часы, звонки и SMS пока не входят в текущий этап.
- Нужны график, текущее значение, локальная тревога, Android-виджет, семейный сайт и Telegram.
- Первые физические датчики: SiBionics GS1, GS1Sb и GS3. Архитектура должна позволять добавлять остальные поддерживаемые семейства.
- Распространение Android-приложения сначала вне Google Play.
- Демо-сайт открыт с тестовыми данными и должен явно обозначать симуляцию.
- Экспериментальные показания нельзя использовать для решений о лечении до физической валидации.
- Пока телефона и датчика нет, выполняется весь программно проверяемый контур.
  После достижения физического барьера работа продолжается над простыми Android
  UI/UX, backend, семейным сайтом и Telegram на тестовых данных.
- `glucose-monitor` ведётся отдельным Git-репозиторием; основной remote —
  `https://github.com/adminhumor-art/helth.git`.

## Текущее состояние

- Работает открытый локальный демо-сайт с симулированным семейным экраном.
- Android-приложение умеет показывать явно обозначенное демо, график, локальные
  демо-тревоги и виджет. Обычный запуск без подтверждённого датчика работает
  fail-closed. Демо-значения не сохраняются, не восстанавливаются после
  перезапуска и не попадают в очередь отправки.
- Backend принимает только продуктовые семейства датчиков, хранит измерения в
  PostgreSQL, формирует тревоги и имеет очередь доставки Telegram. Значения с
  источником `simulator` продуктовый endpoint теперь отклоняет до хранения.
- Android уже соблюдает главный порядок «большое значение → график», но экран настроек тревог отсутствует, свежесть отображается неверно, а график соединяет точки через пропуски.
- Веб сохраняет нужный визуальный порядок, но пока полностью статичен и не получает данные от backend.
- Новый диагностический BLE-драйвер реализует полный программный сеанс GS1 и
  GS1Sb, но ещё не проверен на физическом датчике. Непроверенный общий драйвер,
  который мог публиковать GS3 напрямую, удалён из продуктового модуля. GS3
  остаётся отдельным будущим трактом.
- Официальные нативные наборы алгоритма `v116A`/`v115G` и транспортный
  обработчик уже включены в изолированные Android-модули; их состав и SHA-256
  проверяются до каждой сборки.
- Реализован строгий stateful-адаптер алгоритма: проверка профиля/версии/хеша,
  последовательные индексы, восстановление, закрытие после ошибки и запрет
  следующего шага до подтверждённого сохранения checkpoint.
- Для GS1/GS1Sb команды авторизации, активации, времени и запроса данных теперь
  строит официальный транспортный обработчик. Пакет данных принимается только
  при точном совпадении официального парсера с независимым разбором формата.
- Реализован координатор `sample → алгоритм → атомарное хранилище → подтверждение
  checkpoint`. Сырой пакет, результат, диагностический результат, состояние и
  возможное пользовательское измерение фиксируются одной транзакцией.
- Хранилище обновлено до схемы `v6`: checkpoint содержит семейство, вариант,
  точное происхождение бинарников и canonical MAC физического сенсора. Состояние
  старых схем без доказуемого MAC сохраняется, но помещается в карантин. Для
  каждого ingress отдельно хранится неизменяемый терминальный outcome.
- Перед декодированием каждый принятый BLE notification записывается в отдельный
  append-only ingress-журнал с MAC, attempt, ordinal, временем, полным шифрованным
  пакетом и SHA-256. Только типизированный пакет с таким receipt может войти в
  diagnostic runtime.
- Ошибки входа и неоднозначные исходы записи имеют долговечный журнал. После
  потери ответа базы повторяется та же запись; новая точка её не обгоняет.
- Перед новым Bluetooth-подключением незавершённый ingress восстанавливается в
  порядке фактической последовательности ядра. Разрыв можно закрыть более поздно
  сохранённым точным пакетом; неизвестная протокольная команда остаётся pending
  и блокирует дальнейший replay, а не выбрасывается как «не данные».
- Транспортный пакет сначала проверяется целиком: индексы и время всех точек
  должны быть последовательны. Только затем вызывается алгоритм.
- Повторный аудит официального V120-формата обнаружил и исправил ошибку длины:
  data packet имеет `L=11+8*N`, полный размер `12+8*N`. Декодер теперь требует
  точное `size=L+1`, поэтому не принимает ни обрыв, ни хвост после checksum.
- Создан отдельный diagnostic runtime: неизменяемый профиль с точным MAC,
  generation-защита старых GATT callback, bounded FIFO без скрытого drop,
  последовательный retry pending commit и закрытие ядра после завершения actor.
  После терминального результата уже записанный хвост не передаётся повреждённому
  контексту: его обрабатывает новое поколение через recovery.
- Android GATT-supervisor проверяет точные service/characteristic/CCCD, закрывает
  транспорт до ожидания базы, сохраняет уже принятый хвост в ingress-журнал,
  сериализует записи команд и не зависит от порядка ACK/write callback.
- Для connect, discovery, subscription, command write и handshake действуют
  tokenized deadlines. Повтор auth ограничен тремя попытками; потерянный callback
  не может оставить соединение открытым навсегда.
- Первая терминальная причина соединения неизменяема при гонке callback/actor.
  История и прогрев считаются транспортным прогрессом, но не состоянием свежего
  диагностического значения; стабильность отмечается только по последнему
  `VALID`-результату.
- Retry базы отделён от Bluetooth lifecycle: stop имеет ограниченное ожидание и
  возвращает явное `PersistencePending`, не закрывая неоднозначно изменённое
  нативное состояние. Восстановление соединения использует ограниченный
  exponential backoff и отменяется логически при ручном stop или новом сеансе.
- GS1 state machine теперь проверяет фазу `auth → activation → time → data`,
  поддерживает подтверждённый повтор auth через одну секунду и двигает локальный
  cursor только после долговечного commit.
- До физического допуска factory открывает ядро только в режиме
  `DIAGNOSTIC_ONLY`: сохраняются сырой пакет, расчёт и checkpoint, но обычное
  пользовательское измерение не создаётся. Диагностический кандидат имеет
  отдельный тип и не может случайно попасть в график, тревогу, backend или
  Telegram.
- Повтор точно той же транзакции идемпотентен; конфликтующий дубль и откат
  checkpoint запрещены.
- Реальный сенсорный тракт ещё не подключён к пользовательскому экрану и
  тревогам. Симулятор запускается только отдельным действием «Демо», а драйвер
  GS1/GS1Sb/GS3 остаётся в диагностическом карантине.
- Реальный вызов JNI на ARM, replay и физический датчик ещё не пройдены.
- Текущий APK — тестовая debug-сборка с явным демо и безопасным обычным
  запуском, но ещё не production-сборка для мамы.
- Общая концепция, аудит кода, решения и фактические проверки теперь ведутся раздельно в `PRODUCT_CONCEPT.md`, `CODE_AUDIT.md`, `DECISIONS.md` и `WORKLOG.md`.

## Следующая проверяемая итерация

Рабочий порядок исправлен в `ROADMAP.md`: датчик и ядро идут раньше интерфейса,
backend и Telegram. Эталон, официальные бинарники и базовый JNI/state-контракт
уже закреплены. Программный координатор официального обработчика, алгоритма и
атомарного хранилища создан и закрыт диагностическим выпускным барьером.
Отдельный core runtime, профиль, durable ingress, GATT-supervisor и защита
поколений уже реализованы и покрыты JVM-тестами; Android lint проходит.
Глубокий аудит официальных международного и китайского APK подтвердил native
ABI, состояние, V120-пакет и старт настройки через DataMatrix либо ровно
8 ASCII-символов. Он также выявил отсутствующую часть продукта: доказанный
resolver `код упаковки → BLE identity → точный MAC`. Следующая итерация — этот
onboarding/discovery-контур, ARM-smoke на Android, затем replay и раннее
испытание отдельного датчика. Экран и тревоги подключаются только после
совпадения.

## Аудит исходного эталона

- Код не признан плохим или бесполезным: он содержит важную историю реальной
  эксплуатации, восстановления, протокольных вариантов и исправлений.
- Полный fork не выбран автоматически: проект крупный и монолитный, сенсорный
  путь не отделён в библиотеку, а автоматических replay-тестов SiBionics нет.
- Свободное переписывание сенсорного тракта также отклонено как слишком
  рискованное.
- Граница подтверждена владельцем: полный upstream остаётся read-only эталоном,
  официальное нативное ядро сохраняется, а для продукта создаётся узкий
  Android/JNI-адаптер с доказуемым совпадением.
- Текущие интерфейс, backend и сайт не удаляются; их развитие приостановлено до
  прохождения сенсорных барьеров.

## Исследование подключения SiBionics

- GS1/GS1Sb добавляется сканированием Data Matrix или QR-кода с упаковки. Пользователь затем выбирает региональный вариант протокола; для раздельного комплекта дополнительно сканируется код передатчика.
- GS3 добавляется по коду или NFC. Для датчика, ранее использованного в официальном приложении, нужен тот же числовой SiBionics account ID.
- Для GS3 account ID можно ввести вручную либо получить с сервера SiBionics по email и паролю.
- Проверки аналога подтверждают структуру кода, производителя и модель, BLE-устройство, контрольную сумму пакетов, последовательность протокола и GS3 account binding. Они не подтверждают медицинскую точность показаний.
- Открытое продуктовое решение: должна ли «Сладкая» принимать учётные данные SiBionics для получения GS3 account ID. Без отдельного решения этот поток не реализовывать.

## Критическое ограничение обработки показаний

- Диагностический парсер GS1/GS1Sb теперь возвращает только сырой sample:
  `current`, температуру, индекс, время и `reindex`. Он больше не может выдать
  ток за готовое значение глюкозы.
- Текущий драйвер GS1/GS1Sb нельзя подключать к реальным тревогам или выдавать пользователю как достоверный источник.
- Для GS3 поле-кандидат выделено отдельно, но публикация, последовательность,
  прогрев, свежесть и тренд пока не подтверждены официальным обработчиком и
  replay. Поэтому GS3 также остаётся диагностическим.
- Перед физическим использованием нужен один эталонный вычислительный модуль: точное нативное ядро SiBionics. Одинаковые входные пакеты и состояние должны давать одинаковые значение, тренд и статус.

## Решение по вычислительному ядру

- Владелец подтвердил: для SiBionics используем оригинальное нативное вычислительное ядро SiBionics и не заменяем неизвестную математику собственной реализацией.
- Нашими остаются интерфейс «Сладкой», тревоги, локальное хранение, синхронизация, семейный сайт и backend.
- Ядро изолируется за небольшим интерфейсом и проверяется тестами эквивалентности: один входной пакет и одно состояние должны давать эталонные результат, тренд и статус.
- Реальный вывод GS1/GS1Sb/GS3 остаётся отключённым до успешных тестов эквивалентности и физической проверки.

## Настройка и калибровка

- Нельзя объединять в одно понятие активацию датчика, заводскую калибровку, запись контрольного измерения глюкометром и пользовательскую коррекцию результата.
- GS1 и GS3 заявлены производителем как заводски откалиброванные и не требующие штатной ручной калибровки. Для GS1Sb отдельная официальная инструкция пока не найдена, поэтому его правила нельзя без проверки приравнивать к GS1.
- При инициализации ядра GS1/GS1Sb получает код конкретного сенсора: ровно
  восемь ASCII-символов `A-Z`, `a-z` или `0-9`. Регистр сохраняется; приложение
  не исправляет код и не подставляет другой идентификатор.
- Официальный поток создаёт контекст алгоритма только обычным методом
  инициализации с режимом `0`. Продукт повторяет именно этот путь.
- Чувствительность сначала расшифровывается обычным нативным декодером. Только
  если он вернул ровно `-1.0`, вызывается второй официальный декодер. Это
  fallback декодирования того же кода, а не другой режим инициализации и не
  подстановка другого идентификатора.
- Сейчас продукт допускает к открытию алгоритма только результат декодирования
  `NORMAL` в диапазоне `0.8..2.5`. Результат второго декодера получает отдельную
  метку и отклоняется до отдельного replay и физического
  подтверждения.
- Внутренняя заводская обработка остаётся частью неизменяемого нативного ядра. Ручная коррекция по глюкометру является отдельным постпроцессингом после ядра и не должна менять его сохранённое состояние.
- Исходный результат ядра хранится неизменным. Отдельно должны храниться показанное/скорректированное значение, источник коррекции, единица, время, сенсор, пациент, коэффициенты и версия правила.
- Текущая модель с единственным полем глюкозы недостаточна: по ней нельзя доказать происхождение значения, безопасно пересчитать историю и установить, какое число вызвало тревогу.
- До отдельного решения владельца и набора тестов ручная коррекция не влияет на критические тревоги. Тесты должны отдельно покрывать обычные и прогнозные тревоги, тренд, синхронизацию, Telegram, сайт, удаление коррекции и смену единиц.
- При физической валидации «Сладкая» сначала работает только параллельно с официальным приложением/приёмником. Несовпадение показания с самочувствием проверяется глюкометром; экспериментальное приложение не является единственным источником решения о лечении.

  - китайский GS1 `com.sisensing.sisensingcgm`, версия `02.14.00.00`, SHA-256 `f5b21ab2a1424847b644aaff7a192a1650d4d2ded2ff674f3f7778d12a25f8d2`.
- Оба APK подписаны одним сертификатом `O=sisensing, CN=sisensing`, SHA-256 fingerprint `3F:E0:03:F5:00:2C:9F:4C:03:15:C8:9C:28:9B:07:0A:C7:95:22:0A:45:45:54:23:9F:78:3B:29:62:F2:0F:27`.
- Для наборов `v116A` (международный GS1) и `v115G` (китайский GS1) найдены необходимые алгоритмические и вспомогательные библиотеки для arm64-v8a и armeabi-v7a.
- Выбранные версии `libnative-sensitivity-v110.so` закреплены SHA-256 вместе со

  машинного кода, данных, Build ID и зависимостей. APK проходит 16-КБ
  `zipalign`; runtime на настоящем 16-КБ устройстве остаётся обязательным тестом.
- `libCALCULATION.so` не является частью ядра SiBionics и для текущей задачи не используется.

## Текущие границы проекта

- «Сладкая» создаётся как частное семейное решение для наблюдения за состоянием мамы.
- Публичное распространение, коммерческий выпуск и построение массового сервиса не входят в задачу.
- Производителю SiBionics не пишем. Сначала добиваемся технической работы решения и проверяем его на физическом датчике.
- В коде, интерфейсе и продуктовой документации не должно быть названий сторонних приложений мониторинга.
- Отдельный исследовательский каталог сохраняем полностью: он нужен как технический эталон и не является частью приложения.
- Запрет на упоминания относится прежде всего к исполняемому коду, комментариям и сборке «Сладкой»; исследовательские материалы не удаляем.
## Нативная прослойка SiBionics

- Библиотеки алгоритма предоставляют JNI-интерфейс, а не простой публичный C API.
- Исследованный эталонный путь состоит из трёх частей: транспорт и проверка BLE-пакетов; адаптер JNI и зеркальный объект контекста; оркестрация жизненного цикла алгоритма с восстановлением и сохранением бинарного состояния.
- Значение глюкозы рассчитывает библиотека SiBionics. Внешняя прослойка передаёт индекс измерения, ток, температуру и пороги, затем забирает результат и тренд.
- Алгоритм stateful: после успешной обработки его бинарное состояние сохраняется, а после перезапуска восстанавливается. Статeless-вызов каждого пакета недопустим.
- Для Android-продукта предпочтительный вариант — сначала проверить отдельным тестовым стендом прямой вызов через настоящий Android JNI. Это потенциально позволит заменить крупную эмуляцию Java/JNI небольшой совместимой оболочкой, но решение можно принять только после испытания библиотек и последовательности реальных или записанных пакетов.
- Экспортированные символы и зависимости официальных библиотек подтверждают, что прямой Android JNI для `v116A` и `v115G` технически возможен. ABI-шов следует реализовать минимальными Java-классами с точными именами и типами полей; бизнес-логика от него не зависит.
- Для GS1/GS1Sb используется stateful-путь с нативным алгоритмом. GS3 является отдельным трактом: пакет уже содержит значение глюкозы, поэтому его нельзя насильно проводить через `v116A`/`v115G`.
- В GS1Sb нативный алгоритм вызывается для каждого валидного минутного sample, даже если пользовательское значение публикуется только раз в пять минут. Пропуск или повтор внутреннего шага изменит состояние и последующие результаты.
- Неизвестная модель, прошивка, версия/хеш библиотеки, повреждённое состояние или неоднозначный пакет должны завершаться состоянием «данных нет», а не запасной формулой или догадкой.
- Вызовы одного контекста выполняются строго последовательно. Измерение и новое бинарное состояние фиксируются атомарно; при сбое незавершённый пакет должен быть безопасно воспроизводим.
- Выпускной барьер для каждой подтверждённой модели: точное replay-совпадение результата, тренда, предупреждений и состояния; проверки перезапуска, пропусков, дублей и повреждений; полный жизненный цикл отдельного датчика; длительная фоновая работа на целевом Samsung и контрольном Android другого производителя.
- Полный технический контракт и текущий статус ведутся в
  `SENSOR_CORE_CONTRACT.md`.
