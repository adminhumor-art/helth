# Контракт сенсорного ядра «Сладкой»

Обновлено: 1 августа 2026 года.

Этот документ определяет единственный путь, по которому показание реального
датчика может попасть на экран, в тревогу, на сервер или в Telegram.

## Обязательный поток

```text
BLE-пакет
  → append-only ingress-журнал полного шифрованного notification
  → официальный обработчик транспортных данных
  → независимый разбор того же пакета и точное сравнение результатов
  → проверенный сырой sample: индекс, время, ток, температура, reindex
  → оригинальный нативный алгоритм выбранной версии
  → результат, тренд, предупреждения и новое бинарное состояние
  → одна атомарная запись sample + результата + состояния
  → подтверждение сохранения алгоритму
  → выпускной барьер diagnostic/product
  → публикация только физически допущенного показания
```

Если любой шаг не выполнен однозначно, наружу выходит состояние «нет
проверенных данных», а не вычисленное по догадке число.

## Что сохраняется без изменений

- Официальные нативные библиотеки алгоритма для профилей `v116A` и `v115G`.
- Точные имена Java-классов, JNI-методов, сигнатур и полей контекста, которые
  ожидают эти библиотеки.
- Порядок обработки каждой минутной точки, включая точки, которые не
  публикуются пользователю.
- Бинарное состояние контекста после каждого принятого шага.
- Нативные результат, тренд и коды предупреждений до любого отображения или
  дополнительной коррекции.

## Что делает наш адаптер

- Выбирает профиль и закреплённый набор бинарников по модели и варианту датчика.
- Проверяет вход, последовательность индексов, версию, размер и SHA-256
  сохранённого состояния до вызова JNI.
- Создаёт ровно один последовательный контекст на активный датчик.
- Не принимает следующую точку, пока предыдущее состояние не сохранено.
- Закрывает контекст после ошибки JNI, несовпадения состояния или попытки
  продолжить неоднозначную последовательность.
- Ведёт журнал кода заводской чувствительности, полученного коэффициента, способа
  его декодирования и версии алгоритма.

## Атомарность

Результат измерения нельзя публиковать отдельно от нового состояния алгоритма.
Хранилище должно одной транзакцией записать:

- идентификатор датчика и номер sample;
- время датчика и время телефона;
- сырой ток и температуру;
- исходный результат, тренд и предупреждения;
- профиль, версию и хеш набора нативных библиотек;
- код заводской чувствительности, его источник, коэффициент и способ
  декодирования;
- обычный режим инициализации алгоритма;
- бинарное состояние и его SHA-256.

Только после успешного завершения транзакции адаптер получает подтверждение и
может обрабатывать следующий sample. После сбоя приложение восстанавливается из
последней полностью завершённой транзакции.

Точный повтор уже завершённой транзакции считается успешным идемпотентным
повтором. Другая запись с тем же событием или парой `sensorId + sequence`
является конфликтом и закрывает сессию. Новый checkpoint не может иметь индекс
меньше уже сохранённого.

При неизвестном исходе записи пакет остаётся незавершённым. Новые BLE-пакеты не
обрабатываются, пока точный повтор не подтвердит запись либо не обнаружит
конфликт. Если часть многоточечного пакета уже подтверждена, её индекс и
результаты не теряются.

Перед первым вызовом алгоритма проверяется весь пакет: первая точка должна
совпадать с индексом из checkpoint, остальные индексы идут без разрыва, а время
увеличивается ровно на 60 секунд. Ошибка в поздней точке отклоняет весь пакет до
изменения нативного состояния.

V120 data envelope принимается только целиком: объявленная длина
`L=11+8*N`, фактический размер `L+1`. Один callback — один envelope. Обрыв,
лишний хвост или неверный checksum отклоняются; произвольная склейка соседних
Bluetooth notifications запрещена.

Callback каждого GATT-подключения несёт generation token и принимается только
для точного MAC и того же экземпляра GATT. Stateful-обработка идёт через одну
bounded FIFO. Переполнение завершает поколение, а не скрыто выбрасывает пакет;
повторное подключение затем восстанавливается из долговечного checkpoint.

До декодирования notification получает долговечный ingress receipt. Запись
содержит точный MAC, уникальную попытку подключения, ordinal, время телефона,
полный шифрованный пакет и SHA-256. Runtime типом принимает только пакет с таким
receipt. При терминальной ошибке GATT закрывается сразу, а уже принятый хвост
очереди всё равно дописывается в ingress-журнал и не передаётся закрытому ядру.
После перезапуска pending-ingress обрабатывается до нового live-подключения:

- точный пакет с ожидаемого индекса replay-ится неизменёнными encrypted bytes;
- пакет, полностью покрытый checkpoint, получает `ALREADY_COVERED`;
- доказанный ACK/device-info получает `NON_DATA`, повреждённый пакет —
  `QUARANTINED`;
- разрыв остаётся pending до истории, а неизвестная команда останавливает
  дальнейший replay и не получает ложный терминальный статус;
- outcome фиксируется отдельно и идемпотентно до публикации следующего события.

Терминальный результат stateful-core закрывает admission и не запускает уже
принятый хвост через тот же контекст. Этот хвост остаётся durable evidence для
следующего поколения. Первая терминальная причина неизменяема: более поздний
артефакт закрытого command-arbiter не может заменить исходный retryable-сбой.

Checkpoint дополнительно связан с canonical MAC физического сенсора. Совпадения
логического `sensorId`, семейства и кода упаковки недостаточно для восстановления
state другого устройства. Checkpoint старой схемы без доказуемого MAC хранится
как свидетельство, но нативному алгоритму не передаётся.

Команды GATT проходят через один FIFO-арбитр: одновременно существует не более
одной физической записи. Если ACK приходит раньше Android write callback,
следующая команда ждёт завершения текущей. Все фазы имеют tokenized deadline,
auth retry ограничен, а reconnect использует bounded exponential backoff и
отменяется ручным stop.

Durable commit истории или прогрева подтверждает транспортный прогресс, но не
свежесть медицинского значения. Silence-watchdog переармируется по транспортному
прогрессу; состояние `StreamingDiagnostic` и стабильность reconnect разрешены
только когда последний диагностический результат имеет качество `VALID`.

## Диагностический выпускной барьер

До завершения replay и физического испытания успешный расчёт сохраняет сырой
пакет, полный результат алгоритма и checkpoint, но:

- не создаёт запись в продуктовой таблице измерений;
- всегда имеет `publishable=false` и `alarmEligible=false`;
- возвращается отдельным диагностическим типом, а не `GlucoseReading`;
- не может попасть в график, виджет, тревогу, uploader, сайт или Telegram.

Режим `PRODUCT_RELEASED` включается отдельно для конкретного доказанного
профиля и набора бинарников после прохождения всех выпускных барьеров.

## Чувствительность и калибровка

- Код конкретного сенсора проверяется первым: ровно восемь ASCII-букв или цифр.
  Регистр сохраняется, другой идентификатор не подставляется.
- Официальный поток создаёт контекст алгоритма обычным JNI-методом в режиме `0`.
  Продукт использует только этот способ инициализации.
- Обычный декодер чувствительности вызывается первым. Второй официальный
  декодер вызывается только при точном результате `-1.0` и получает тот же код.
  Это fallback декодирования, а не отдельная инициализация.
- Сейчас продукт открывает алгоритм только для результата `NORMAL` в диапазоне
  `0.8..2.5`. Иной тип декодирования завершается явной ошибкой до отдельного
  replay и физического подтверждения.
- Заводская чувствительность внутри оригинального ядра не смешивается с будущей
  пользовательской коррекцией по глюкометру.

## Разные семейства

- GS1 и GS1Sb используют stateful-алгоритм. Их сырой ток никогда не считается
  готовой глюкозой.
- GS3 имеет отдельный транспорт и отдельные правила публикации. Он не
  проводится через алгоритм GS1/GS1Sb и не допускается к тревогам только потому,
  что в пакете найдено похожее на глюкозу поле.

## Выпускные барьеры

Реальный профиль получает статус «допущен» только после всех проверок:

1. Хеши бинарников, JNI ABI и зависимости совпадают с закреплённым набором.
2. Replay даёт одинаковые результат, тренд, предупреждения и состояние на каждом
   шаге, включая перезапуск и восстановление.
3. Пропуск, дубль, повреждённый пакет, повреждённое состояние и ошибка записи
   завершаются без публикации нового числа.
4. Отдельный физический датчик проходит полный жизненный цикл на Samsung и ещё
   одном Android-устройстве.
5. Проверены фон, блокировка экрана, перезагрузка, обновление приложения,
   временная потеря Bluetooth и восстановление истории.
6. Только после этого показание подключается к локальным тревогам, сайту и
   Telegram.

## Текущий статус

- JNI ABI, закрепление бинарников и чистая оркестрация состояния реализованы и
  покрыты локальными тестами.
- Официальный обработчик транспортных данных упакован, его ABI закреплён; он
  строит команды GS1/GS1Sb и разбирает ответы.
- Приём GS1 использует двойную проверку: официальный и независимый парсеры
  должны дать полностью одинаковые входы алгоритма.
- Реализованы обычная инициализация в режиме `0`, строгая политика 8-символьного
  кода и декодирование чувствительности. Неподтверждённый способ декодирования
  продукт не принимает.
- Реализовано атомарное Room-хранилище с идемпотентным повтором, обнаружением
  конфликтующего дубля и запретом регрессии checkpoint.
- Схема checkpoint хранит происхождение транспорта; недоказуемое состояние
  старой схемы переносится без потери, но блокируется до явного восстановления.
- Реализованы журнал отказов, точный повтор неопределённой записи, целостная
  предварительная проверка пакета и последовательная обработка без обгона.
- Factory принудительно открывает физически непроверенный тракт в
  `DIAGNOSTIC_ONLY`; тест подтверждает отсутствие записи в продуктовом
  репозитории измерений.
- Реализованы отдельный FIFO-runtime, durable ingress и generation gate. Тесты доказывают
  игнорирование старого callback, точный retry до следующего notification,
  drain при stop, fail-closed overflow и запрет product reading в
  диагностическом runtime.
- Реализованы долговечные outcomes и restart recovery до live GATT. Неизвестная
  команда остаётся pending, разрыв может быть закрыт более поздним сохранённым
  пакетом, а терминальный core-result оставляет хвост следующему поколению.
- Координатор включён в диагностический GATT-поток GS1/GS1Sb через строгий
  профиль, append-only ingress, command arbiter, deadlines и reconnect. Он не
  включён в UI, тревоги или отправку наружу.
- ARM64-библиотеки механически выровнены под 16-КБ страницы с сохранением
  машинного payload, Build ID и зависимостей; исходные и итоговые SHA-256
  записаны в `NATIVE_BINARY_PROVENANCE.md`.
- GS1/GS1Sb и GS3 остаются в диагностическом карантине и не управляют экраном
  или тревогами. Обычный Android-запуск работает fail-closed; симулятор доступен
  только отдельным явно обозначенным демо-действием и не сохраняется/не
  отправляется.
- Реальный ARM-вызов JNI, replay и физический датчик ещё не пройдены. Поэтому
  текущий APK использует только явно обозначенный симулятор.
